• A) Rapid expand/collapse (same axis)

    a - abort the request
  - Q-A2: If we abort, do we still want to keep any partial response that already arrived (streaming not applicable, but
    chunks may arrive) or treat as “no data”?

  - Q-A3: If the response returns after collapse, should we still merge it into the in-memory data cache (warm re-expand) as
    long as filterSignature matches?
    I guess same as the above - keep it in cache
  - Q-A4: If we keep it as cache-warm, do we cap “wasted work” (e.g. don’t warm-cache if user collapsed within <200ms)?
  Not sure what you mean, explain if further and give options and their conceqences.
  - Q-A5: If the user re-expands immediately after collapsing, should the UI reuse the in-flight request (dedupe by specId)
    instead of re-issuing?
    Well, i case there is cache, we just use cache. I don't think that it is reasonble to write delays and do complex logic for this case, just issue another request. If there are any other such cases in the codebase (that have to do with timing), highlight them to me
  - Q-A6: If a child fetch is in-flight and the user collapses the parent, do we cancel all descendant in-flight fetches
    automatically?
    Yep
  - Q-A7: If the user collapses a node while multiple sibling batch fetches are in-flight, do we allow the batch to continue
    (since it also serves other siblings) or do we split/cancel?
    This is a hard one, present options
  - Q-A8: Should “collapse” immediately remove children rows from the committed view (optimistic collapse), or wait until
    pending state converges?
    Expand on this
  - Q-A9: Should “expand” immediately show empty child placeholders (optimistic expand) or only show spinner on header cell
    until data arrives?
    No, we never show empty cells. We only expand when we know we can fully fill the expanded area. It may be two step expand, like lets say a user expanded rows and columns, and with the current responses we can already expand the columns. Then we expand the columns (stop its loader), then wait, then expand the rows. About the loader, here technically the column node still sends requests, but we stop the loader as soon as the node is expanded. And we only show loaders for expansions, they do not represent quesries made to the database. They are tied to user intent, so a row expansion should not trigger a column loader.
  - Q-A10: What is the rule for the per-node spinner when toggles happen rapidly (e.g. expand→collapse→expand): last-intent
    wins, but should spinner persist continuously or reset?
    Persisting continuously is fine. But in the above case, on the collapse the loader will stop, becasue cached values will be instantly loaded, as we stated from the collapsed state.

  D) Runtime layout builder (drag/drop fast, many operations)

  - Q-D1: Do layout changes apply on drop only, or do we preview live while dragging (would trigger many plans)?

  - Q-D2: If the user drags multiple dimensions quickly (drop, pick again, drop), do we (a) start a transaction per drop, (b)
    debounce and only execute last drop?
    the thing is it depends on layer of the drop. In simplest case when new dimesion is put at the bottom we do not do anything as it is deeper than current expansion. When change is destructive, we collapse the pivot to the last cached expansion and still don't do anything. And only if the new dimesion is the first in the stack then we do a request to get that dimesion. But otherwise, collapse all the destroyed layers, add [+] where new layers appear, but no queries.
  - Q-D3: If a layout transaction is pending and the user drags again, do we cancel pending fetches and start new, or allow

  - Q-D5: For reordering dimensions within an axis: do we treat as destructive (prune expansions) or attempt a migration

  - Q-D6: If the user removes a dimension (shrinks depth), do we keep its expansions “remembered” in case they add it back

  - Q-D7: If the user adds a dimension at the end (non-destructive), do we automatically prefetch children for all currently-
